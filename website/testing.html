02

How programs were tested

Fresh container for every test

  • Linux runner image pinned by digest.
  • No network, non-root users and read-only source mount.
  • 256 MiB memory limit, one CPU and process/output limits.
  • Compilation and execution are separate phases.
  • Expected output stays on the host.

Failure cases covered

  • Correct output and wrong answers.
  • Syntax errors and runtime exceptions.
  • CPU time, memory and output limits.
  • Process cleanup and fresh test state.
  • Cancellation and owner-scoped orphan cleanup.

03

From saved response to hidden score

Durable request accounting

Request intent is stored before dispatch. Raw responses are saved before parsing and judging. A missing response is marked unknown instead of being silently retried.

Completed resume was checked separately: two calls before and after, with no additional inference.

Completed-resume check

Sealed evaluation

A seal binds the selected plan, resolved setup, task records, artifact hashes and logical database state. The evaluator checks the seal before and after hidden judging.

The 15-trial view has complete call/token coverage, no selected unknown usage and no censored checkpoints.

What a passing test means here

Fixture tests verify harness behavior. Reference checks verify the chosen suites against vetted solutions. The model benchmark measures returned-program success on five hidden cases per problem. Each is useful evidence for a different part of the work.
