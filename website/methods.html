Methods

How the search works, and the two changes to REx.

A program is an arm. Repair-test pass fraction is its score, h. The root is the option to generate a fresh program. REx decides which arm to try next.

01

The three search methods

Always generate from the root prompt. Test each completed program and retain the best repair score. There is no branch refinement.

Maintain a bank of programs. Sample from a Beta distribution for each eligible arm, then generate from the root or repair a selected program.

Use the same candidate bank and model. Add positive partial-progress credit to the update and normalize selection by estimated token cost.

02

The two changes

A

Give credit to an improvement

Baseline REx gives an incomplete repair no success credit. The extension gives fractional credit when a non-root repair improves its parent without yet passing every repair test.

r = η × max(0, hchild − hparent)
α ← α + r    β ← β + (1 − r)

Root partial generations receive zero progress credit. Full repair success is saved and stops before updating the parent, following the upstream terminal rule.

B

Account for the next request’s cost

Baseline REx selects the largest Beta sample. The extension divides that sample by estimated tokens raised to γ.

priority = θ / max(1, estimated tokens)γ
θ ~ Beta(α, β)    α = 1 + C·h    β = 1 + C·(1 − h)

The estimate starts at prompt characters / 4 + 512 output tokens, then adapts using past requests within that trial. Actual reported costs use backend token counts.

04

Shared rules

  • All methods use the same model, prompts, parser, repair tests and Docker limits.
  • Repair feedback includes one independently selected failing test from the current candidate.
  • The returned solution is the completed eligible program with the highest repair score. Earlier creation breaks ties.
  • Malformed and duplicate generations still consume calls and tokens.
  • Full repair success stops search. Otherwise the pilot targets eight calls and token coverage; the per-trial extension ceiling is sixteen calls.
  • Hidden results never select, rank or repair a program during search.
Implementation and original source

The REx scheduler is reproduced from the pinned upstream implementation. The controlled APPS wrapper has documented differences, including one arm per generation and explicit charging of invalid outputs. Progress shaping is a heuristic pseudo-count update, without an exact-posterior or optimality guarantee.
